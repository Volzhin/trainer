# Разработка и деплой

Инструкция для тех, кто вносит правки и выкладывает их в прод.

## Что это устроено как

| Слой | Чем сделан | Где живёт |
| --- | --- | --- |
| Приложение | React 18 + TypeScript + Vite, без UI-библиотеки | `src/` |
| Локальная база | Dexie (IndexedDB) — источник правды на устройстве | `src/db/db.ts` |
| Бэкенд | PocketBase: аккаунты, права, файлы, живые обновления | `/opt/trainer/pb` на сервере |
| Схема бэкенда | Обычный скрипт, применяется при каждом деплое | `server/schema.mjs` |
| Серверные обработчики | JS-хуки PocketBase | `server/pb_hooks/` |

Приложение офлайн-первое. Человек работает с локальной базой, а обмен с
сервером идёт фоном: выгружает изменённое и забирает чужое. Конфликты
решаются по `updated_at` — побеждает более поздняя запись. Держите это в
голове: **экраны читают Dexie, а не сеть**, и перерисовываются сами, когда
в базу что-то приходит.

## Что нужно поставить

- Node 22 или новее
- `gh` — GitHub CLI, для доступа к репозиторию

```bash
git clone https://github.com/Volzhin/trainer.git
cd trainer
npm ci
npm run dev
```

Локально приложение поднимется на `http://localhost:5173` и будет ходить в
прод-бэкенд. Регистрируйтесь отдельным тестовым адресом, а не аккаунтом
живого пользователя.

Перед коммитом:

```bash
npx tsc -b          # проверка типов, обязательна
npm run build       # то же самое сделает деплой
npx prettier --write "src/**/*.{ts,tsx}"
```

## Доступ к репозиторию

Владелец добавляет соавтора один раз:

```bash
gh api -X PUT repos/Volzhin/trainer/collaborators/ЛОГИН -f permission=push
```

Или в интерфейсе: `Settings → Collaborators → Add people`, права **Write**.
Приглашение придёт на почту, его нужно принять.

Права `Write` дают пуш в `main` и запуск деплоя. **Считайте, что они же
дают и доступ к секретам:** секреты видны любому workflow, а workflow
запускается пушем в `main`. Кто может пушить — тот может добавить шаг,
печатающий `DEPLOY_KEY` в лог. Ключ у нас от `root`, поэтому право записи
в репозиторий равнозначно root-доступу к серверу, где живёт ещё и чужой
проект. Дело не в доверии к человеку: одной уведённой учётки GitHub хватит.

Пока так и оставлено сознательно — ради того, чтобы выкладывать мог каждый
без ожидания подтверждений. Чем это чинится, когда руки дойдут:

- деплоить не под `root`, а под отдельным пользователем с правами только
  на `/opt/trainer`;
- ограничить ключ в `authorized_keys` через `command="..."`, чтобы им
  нельзя было сделать ничего, кроме самой выкладки.

Оба способа никого не тормозят и подтверждений не добавляют. А вот защиту
ветки `main` с обязательным ревью включать не нужно — она как раз потребует
подтверждения на каждый пуш.

## Права доступа к GitHub

Деплой описан файлом в `.github/workflows/`. GitHub не даёт OAuth-приложениям
править такие файлы без отдельного разрешения, поэтому **один раз** выполните:

```bash
gh auth refresh -h github.com -s workflow
```

Без этого пуш, затрагивающий `.github/workflows/deploy.yml`, будет отклонён
с сообщением `refusing to allow an OAuth App to create or update workflow`.
Все остальные правки пушатся обычным образом.

Команда безобидная, но пропускать её не стоит: однажды на этом уже
потерялись — файл деплоя месяц лежал закоммиченным на одной машине и не
мог уехать на GitHub, а пуши в `main` тем временем не запускали ничего,
и выглядело это как «деплой сломался».

## Как выкладывать

**Единственный способ — пуш в `main`.**

```bash
git add -A
git commit -m "что и почему"
git push origin main
```

Дальше GitHub Actions сам:

1. проверяет типы;
2. собирает приложение;
3. кладёт статику на сервер;
4. обновляет серверные обработчики и перезапускает PocketBase;
5. применяет схему базы;
6. проверяет, что API отвечает.

Смотреть ход: `gh run watch`. Если шаг упал — прод остаётся на предыдущей
версии, потому что статика выкладывается раньше схемы, а схема идемпотентна.

**Не выкладывайте руками через `rsync` или `scp`.** На сервере окажется код,
которого нет в репозитории, и следующий же деплой его затрёт — вместе с
пониманием, что вообще сейчас работает у пользователей.

## Секреты

В настройках репозитория (`Settings → Secrets and variables → Actions`):

| Секрет | Что это |
| --- | --- |
| `DEPLOY_KEY` | приватный SSH-ключ для доступа на сервер |
| `DEPLOY_HOST` | IP сервера |
| `DEPLOY_DOMAIN` | домен, по которому проверяется живость |
| `SSH_KNOWN_HOSTS` | отпечаток сервера (см. ниже) |
| `PB_ADMIN_EMAIL` | администратор PocketBase |
| `PB_ADMIN_PASSWORD` | его пароль |

`SSH_KNOWN_HOSTS` пока необязателен, но задать его стоит. Без него деплой
снимает отпечаток сервера заново на каждом запуске и доверяет тому, кто
ответил, — то есть посредник между раннером GitHub и сервером получил бы и
доступ по SSH, и пароль администратора базы. Снять отпечаток один раз:

```sh
ssh-keyscan -H <IP сервера>
```

и вставить вывод целиком в секрет. Пока секрет пуст, деплой продолжает
работать по-старому и пишет об этом предупреждение в лог сборки.

**Ничего из этого не должно попадать в репозиторий.** Пароли от сервера и
админки спрашивайте у Ивана лично. Файл `ssh.md` намеренно в `.gitignore` —
не убирайте его оттуда и не коммитьте доступы «временно».

## Сервер

На той же машине живёт чужой проект — Streamlit на `seo-volzhin.fun`.
**Его не трогаем.** Наше хозяйство:

| Что | Где |
| --- | --- |
| Служба бэкенда | `trainer-pb` |
| Данные и файлы | `/opt/trainer/pb/pb_data` |
| Обработчики | `/opt/trainer/pb/pb_hooks` |
| Статика | `/opt/trainer/web` |
| Конфиг nginx | `/etc/nginx/sites-available/trainer` |

Полезное:

```bash
systemctl status trainer-pb
journalctl -u trainer-pb -n 50 --no-pager   # логи бэкенда
systemctl restart trainer-pb                 # после правки хуков
nginx -t && systemctl reload nginx           # после правки конфига
```

Админка PocketBase — `/_/` на домене приложения. Там видно все коллекции,
записи и файлы, и оттуда же делаются резервные копии.

## Как менять схему базы

Схема бэкенда описана в `server/schema.mjs`. Правьте **его**, а не админку:
клики по интерфейсу нигде не сохраняются, и при следующем деплое схема
разъедется с приложением. Скрипт идемпотентен — досылает только разницу.

Локальная схема Dexie версионируется в `src/db/db.ts`. Два правила:

- версии объявляются **строго по возрастанию**;
- уже выпущенную версию **не переписывают** — Dexie не применит её повторно,
  нужна новая.

## Что синхронизируется

Наверх уезжает только то, у чего есть настоящий владелец: профиль,
тренировки, подходы, замеры, питание, личные программы, назначения,
заметки, обратная связь, вложения.

**Не синхронизируются намеренно:**

- `exercises` — каталог из 1061 упражнения, одинаков у всех, приезжает из
  статики при первом запуске;
- программы каталога — тоже общие, поэтому их идентификаторы выводятся из
  состава (`prog-0`, `rt-0-1`), а не выдаются случайно: иначе назначенная
  тренером программа ссылалась бы у клиента в пустоту;
- `appState` — настройки конкретного устройства;
- `syncQueue` — служебная очередь.

Добавляете новую таблицу с пользовательскими данными — впишите её в `SYNCED`
в `src/db/sync.ts` и определите владельца в `ownerOf`. Владелец `null`
означает «не наше, не отправляем»; возвращать текущего пользователя
«на всякий случай» нельзя — так однажды на сервер уехал весь каталог.

## Права доступа

Тренер видит и правит данные своих клиентов, больше ничьи. На сервере это
одно правило: `owner = @request.auth.id || owner.trainer = @request.auth.id`.
Связь — поле `trainer` в аккаунте клиента, оно же источник правды для списка
клиентов у тренера.

Коды приглашений закрыты полностью: клиент их не ищет, а отдаёт серверу
через `POST /api/redeem`. Открытый список означал бы, что любой вошедший
может выгрузить чужие коды и привязаться к незнакомому тренеру.

## Если что-то пошло не так

**У пользователя старая версия.** Приложение — PWA, его держит service
worker. Попросите закрыть вкладку и открыть заново или обновить с очисткой
кеша. На телефоне надёжнее закрыть вкладку.

**Данные не доезжают до второй стороны.** Смотрите в админке коллекцию
`records`: есть ли там нужная строка и правильный ли у неё `owner`. Если
строки нет — она не прошла отправку; если владелец не тот — ошибка в
`ownerOf`.

**Не приходят живые обновления.** Проверьте, что nginx не буферизует поток:
в конфиге должны быть `proxy_buffering off` и длинный `proxy_read_timeout`.

**Письма не приходят.** SMTP не настроен вовсе. Пока это так, ссылка
«забыли пароль» скрыта флагом `VITE_MAIL_ENABLED`. Когда ящик подключат,
включите флаг в сборке.

## Чего пока нет

Список открытых задач, чтобы не браться за них вслепую:

- запросы к базе продуктов Open Food Facts уходят из браузера напрямую за
  рубеж — нужен прокси через свой сервер с кешем;
- отправка сканирует таблицы целиком: по `updated_at` нет индекса, на
  больших объёмах будет тормозить телефон;
- SMTP не подключён;
- требования по персональным данным (152-ФЗ) не реализованы: нет согласий
  с версионированием, журнала доступа, экспорта данных и разделения
  идентифицирующих и медицинских сведений. Сервер не в аттестованном
  контуре, поэтому **на живых данных клиентов работать нельзя** — только на
  тестовых.
