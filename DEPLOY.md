# Разработка и деплой

Инструкция для тех, кто вносит правки и выкладывает их в прод.

## Что это устроено как

| Слой | Чем сделан | Где живёт |
| --- | --- | --- |
| Приложение | React 18 + TypeScript + Vite, без UI-библиотеки | `src/` |
| Локальная база | Dexie (IndexedDB) — источник правды на устройстве | `src/db/db.ts` |
| Бэкенд | PocketBase: аккаунты, права, файлы, живые обновления | `/opt/trainer/pb` на сервере |
| Схема бэкенда | Обычный скрипт, применяется при каждом деплое | `server/schema.mjs` |
| Серверные обработчики | JS-хуки PocketBase | `server/pb_hooks/` |

Приложение офлайн-первое. Человек работает с локальной базой, а обмен с
сервером идёт фоном: выгружает изменённое и забирает чужое. Конфликты
решаются по `updated_at` — побеждает более поздняя запись. Держите это в
голове: **экраны читают Dexie, а не сеть**, и перерисовываются сами, когда
в базу что-то приходит.

## Что нужно поставить

- Node 22 или новее
- `gh` — GitHub CLI, для доступа к репозиторию

```bash
git clone https://github.com/Volzhin/trainer.git
cd trainer
npm ci
npm run dev
```

Локально приложение поднимется на `http://localhost:5173` и будет ходить в
прод-бэкенд. Регистрируйтесь отдельным тестовым адресом, а не аккаунтом
живого пользователя.

Перед коммитом:

```bash
npx tsc -b          # проверка типов, обязательна
npm run build       # то же самое сделает деплой
npx prettier --write "src/**/*.{ts,tsx}"
```

## Доступ к репозиторию

Владелец добавляет соавтора один раз:

```bash
gh api -X PUT repos/Volzhin/trainer/collaborators/ЛОГИН -f permission=push
```

Или в интерфейсе: `Settings → Collaborators → Add people`, права **Write**.
Приглашение придёт на почту, его нужно принять.

Права `Write` дают пуш в `main` и запуск деплоя. **Считайте, что они же
дают и доступ к секретам:** секреты видны любому workflow, а workflow
запускается пушем в `main`. Кто может пушить — тот может добавить шаг,
печатающий `DEPLOY_KEY` в лог. Ключ у нас от `root`, поэтому право записи
в репозиторий равнозначно root-доступу к серверу, где живёт ещё и чужой
проект. Дело не в доверии к человеку: одной уведённой учётки GitHub хватит.

Пока так и оставлено сознательно — ради того, чтобы выкладывать мог каждый
без ожидания подтверждений. Чем это чинится, когда руки дойдут:

- деплоить не под `root`, а под отдельным пользователем с правами только
  на `/opt/trainer`;
- ограничить ключ в `authorized_keys` через `command="..."`, чтобы им
  нельзя было сделать ничего, кроме самой выкладки.

Оба способа никого не тормозят и подтверждений не добавляют. А вот защиту
ветки `main` с обязательным ревью включать не нужно — она как раз потребует
подтверждения на каждый пуш.

## Права доступа к GitHub

Деплой описан файлом в `.github/workflows/`. GitHub не даёт OAuth-приложениям
править такие файлы без отдельного разрешения, поэтому **один раз** выполните:

```bash
gh auth refresh -h github.com -s workflow
```

Без этого пуш, затрагивающий `.github/workflows/deploy.yml`, будет отклонён
с сообщением `refusing to allow an OAuth App to create or update workflow`.
Все остальные правки пушатся обычным образом.

Команда безобидная, но пропускать её не стоит: однажды на этом уже
потерялись — файл деплоя месяц лежал закоммиченным на одной машине и не
мог уехать на GitHub, а пуши в `main` тем временем не запускали ничего,
и выглядело это как «деплой сломался».

## Как выкладывать

**Единственный способ — пуш в `main`.**

```bash
git fetch origin                     # обязательно, до всего остального
git log --oneline main..origin/main  # пусто? тогда можно
git add -A
git commit -m "что и почему"
git push origin main
```

**Сверяйтесь с `origin/main` перед каждой выкладкой.** В `main` пишут
несколько человек, а защиты ветки нет сознательно (см. выше) — значит
единственное, что удерживает от расхождения, это привычка. Если
`main..origin/main` не пуст, сначала подтяните чужое:

```bash
git pull --rebase origin main
npx tsc -b && npm run build          # чужие правки могли задеть ваши
```

Цена промаха здесь выше обычной: пуш деплоится сразу, поэтому конфликт
разъезжается не в рабочей копии, где его видно, а в проде. Особенно легко
столкнуться в `src/index.css` и `src/tokens.css` — общие файлы, которые
трогает почти любая задача по внешнему виду.

Пуш «через силу» (`--force`, `--force-with-lease`) в `main` не делают
никогда: он стирает чужую работу и запускает деплой кода, которого больше
ни у кого нет.

### Хук с проверкой типов

Само расхождение git ловит и без нас: если `origin/main` ушёл вперёд, пуш
перестаёт быть fast-forward и отбивается. Отдельный хук на это не нужен.

Чего git **не** ловит — это пуш сразу после `git pull --rebase`, когда
чужое влито, конфликт разрешён руками, а пересобрать забыли. Такой пуш
уходит в деплой и валит его. Ловится хуком `.git/hooks/pre-push` (лежит вне
репозитория, ставится на каждой машине отдельно):

```sh
#!/bin/sh
remote="$1"
z40=0000000000000000000000000000000000000000
while read -r _l local_sha remote_ref _rs; do
  [ "$remote_ref" = refs/heads/main ] || continue
  [ "$local_sha" = "$z40" ] && continue
  echo "pre-push: проверяю типы перед выкладкой в main…"
  if ! npx tsc -b; then
    echo "ОТКАЗ: tsc не проходит — этот код не соберётся и на деплое."
    exit 1
  fi
  break
done
exit 0
```

```bash
chmod +x .git/hooks/pre-push
```

Обойти, когда правда нужно: `git push --no-verify`.

Дальше GitHub Actions сам:

1. проверяет типы;
2. собирает приложение;
3. кладёт статику на сервер;
4. обновляет серверные обработчики и перезапускает PocketBase;
5. применяет схему базы;
6. проверяет, что API отвечает.

Смотреть ход: `gh run watch`. Если шаг упал — прод остаётся на предыдущей
версии, потому что статика выкладывается раньше схемы, а схема идемпотентна.

**Не выкладывайте руками через `rsync` или `scp`.** На сервере окажется код,
которого нет в репозитории, и следующий же деплой его затрёт — вместе с
пониманием, что вообще сейчас работает у пользователей.

## Секреты

В настройках репозитория (`Settings → Secrets and variables → Actions`):

| Секрет | Что это |
| --- | --- |
| `DEPLOY_KEY` | приватный SSH-ключ для доступа на сервер |
| `DEPLOY_HOST` | IP сервера |
| `DEPLOY_DOMAIN` | домен, по которому проверяется живость |
| `SSH_KNOWN_HOSTS` | отпечаток сервера (см. ниже) |
| `PB_ADMIN_EMAIL` | администратор PocketBase |
| `PB_ADMIN_PASSWORD` | его пароль |

`SSH_KNOWN_HOSTS` пока необязателен, но задать его стоит. Без него деплой
снимает отпечаток сервера заново на каждом запуске и доверяет тому, кто
ответил, — то есть посредник между раннером GitHub и сервером получил бы и
доступ по SSH, и пароль администратора базы. Снять отпечаток один раз:

```sh
ssh-keyscan -H <IP сервера>
```

и вставить вывод целиком в секрет. Пока секрет пуст, деплой продолжает
работать по-старому и пишет об этом предупреждение в лог сборки.

**Ничего из этого не должно попадать в репозиторий.** Пароли от сервера и
админки спрашивайте у Ивана лично. Файл `ssh.md` намеренно в `.gitignore` —
не убирайте его оттуда и не коммитьте доступы «временно».

## Сервер

На той же машине живёт чужой проект — Streamlit на `seo-volzhin.fun`.
**Его не трогаем.** Наше хозяйство:

| Что | Где |
| --- | --- |
| Служба бэкенда | `trainer-pb` |
| Данные и файлы | `/opt/trainer/pb/pb_data` |
| Обработчики | `/opt/trainer/pb/pb_hooks` |
| Статика | `/opt/trainer/web` |
| Конфиг nginx | `/etc/nginx/sites-available/trainer` |

Полезное:

```bash
systemctl status trainer-pb
journalctl -u trainer-pb -n 50 --no-pager   # логи бэкенда
systemctl restart trainer-pb                 # после правки хуков
nginx -t && systemctl reload nginx           # после правки конфига
```

Админка PocketBase — `/_/` на домене приложения. Там видно все коллекции,
записи и файлы, и оттуда же делаются резервные копии.

### Администраторы базы

Заводятся на сервере, по одному на человека:

```bash
/opt/trainer/pb/pocketbase superuser upsert ПОЧТА 'ПАРОЛЬ'
/opt/trainer/pb/pocketbase superuser list
/opt/trainer/pb/pocketbase superuser delete ПОЧТА
```

**Это не то же самое, что аккаунт в приложении.** Администраторы живут в
отдельной коллекции `_superusers` со своими паролями; учётка на ту же почту
в приложении — другая запись, и роль `trainer` к правам администратора
отношения не имеет.

Прежде чем добавлять ещё один такой ключ, взвесьте, что он открывает:
**всю базу целиком** — переписку, отчёты, фотографии людей, почты, — и
резервную копию, которую можно скачать одним запросом. Поэтому:

- пароль задаёт сам человек или меняет его при первом входе; чужой пароль
  не придумывают за него и не пересылают в переписке;
- многофакторность у администраторов включить нельзя, пока не подключён
  SMTP: письма отправлять нечем. Единственная защита пароля — счётчик
  неудач в `login-throttle.pb.js` (пять подряд закрывают вход на минуту) и
  правило частоты `*:auth`;
- админка `/_/` открыта из интернета и правами PocketBase защищена только
  на уровне «нужен пароль». Ограничение по адресу делается конфигом nginx
  либо настройкой `superuserIPs` — второе запирает снаружи и вас самих,
  если ошибётесь адресом, вернуться можно будет только с сервера.

## Как менять схему базы

Схема бэкенда описана в `server/schema.mjs`. Правьте **его**, а не админку:
клики по интерфейсу нигде не сохраняются, и при следующем деплое схема
разъедется с приложением. Скрипт идемпотентен — досылает только разницу.

Локальная схема Dexie версионируется в `src/db/db.ts`. Два правила:

- версии объявляются **строго по возрастанию**;
- уже выпущенную версию **не переписывают** — Dexie не применит её повторно,
  нужна новая.

## Что синхронизируется

Наверх уезжает только то, у чего есть настоящий владелец: профиль,
тренировки, подходы, замеры, питание, личные программы, назначения,
заметки, обратная связь, вложения.

**Не синхронизируются намеренно:**

- `exercises` — каталог из 1061 упражнения, одинаков у всех, приезжает из
  статики при первом запуске;
- программы каталога — тоже общие, поэтому их идентификаторы выводятся из
  состава (`prog-0`, `rt-0-1`), а не выдаются случайно;
- `appState` — настройки конкретного устройства;
- `syncQueue` — служебная очередь.

Выведенных идентификаторов, однако, недостаточно, чтобы назначение доехало.
Каталог одинаков только у одинаковых сборок: у клиента с версией постарше
назначенной программы нет вовсе, и ссылка ведёт в пустоту — он видит пустой
календарь, пока тренер видит «назначено», и проверить это со стороны тренера
нельзя, у него на устройстве всё сходится. Поэтому назначение копирует
программу под клиента **в том числе из каталога** (`programForClient` в
`src/db/coach.ts`): копия принадлежит клиенту и едет обменом как обычная
строка.

Добавляете новую таблицу с пользовательскими данными — впишите её в `SYNCED`
в `src/db/sync.ts` и определите владельца в `ownerOf`. Владелец `null`
означает «не наше, не отправляем»; возвращать текущего пользователя
«на всякий случай» нельзя — так однажды на сервер уехал весь каталог.

## Ограничение частоты и перебор паролей

Две разные защиты, и они закрывают разное.

**Встроенный лимитер PocketBase** считает запросы по адресу клиента, держит
счётчики в памяти процесса и настраивается из `server/schema.mjs`
(`applyLimits`). Отдельного хранилища вроде Redis не нужно и его нет: сервер
один, а переживать перезапуск счётчикам незачем. Правила: вход — 5 запросов
за 5 секунд, `/api/redeem` и `/api/unlink` — 10 в минуту, общий потолок по
`/api/` — 300 за 10 секунд (обмен ходит пачками, потолок должен быть щедрым).

**Включается переменной `PB_RATE_LIMITS=on`** у шага схемы в деплое (она там
уже стоит). Без неё деплой выставит `enabled: false` — это не забывчивость,
а защита:

> Лимитер считает по адресу клиента, а за nginx все запросы приходят с адреса
> самого nginx. Пока PocketBase не знает, какому заголовку верить, все
> пользователи для него — один клиент: двое вошли, третий получил отказ.

Поэтому `applyLimits` заодно ставит `trustedProxy.headers = ['X-Forwarded-For']`.
Берётся ближний к серверу адрес (`useLeftmostIP: false`): крайний левый в
`X-Forwarded-For` присылает клиент, и подделать его может кто угодно, а
правый дописывает наш же nginx.

Что это работает, проверено снаружи временным ответом `/api/whoami` (снят,
см. `whoami.pb.js`): сервер видит публичный адрес клиента, а не адрес nginx,
и подставленный в запрос `X-Forwarded-For` результат не меняет. Если будете
менять конфиг nginx или переносить сервер — проверьте заново тем же способом,
прежде чем полагаться на лимиты.

Обойти nginx и подставить свой заголовок напрямую нельзя: бэкенд слушает
только петлю — `LISTEN 127.0.0.1:8090`, — а снаружи порт закрыт (проверено
соединением с раннера GitHub: `Connection refused`). Наружу смотрит только
nginx, на 80 и 443. **Если когда-нибудь переселите бэкенд или откроете ему
порт — ограничение по адресу перестанет что-либо значить**, потому что
заголовку сервер верит без оговорок; проверяйте `ss -ltnp | grep 8090` после
любых работ с сетью.

**Перебор пароля по одному ящику** встроенный лимитер не видит — с десяти
машин придёт по паре запросов, и каждая уложится в порог. Этим занимается
`server/pb_hooks/login-throttle.pb.js`: считает неудачи по нормализованному
адресу почты в `$app.store()` (встроенное потокобезопасное хранилище в
памяти). Пять неудач подряд — минута, десять — пять минут, пятнадцать —
пятнадцать. Удачный вход обнуляет счётчик, час без попыток — тоже.

Важные решения, которые не надо «улучшать» не подумав:

- блокируются **попытки входа, а не учётная запись**. Иначе посторонний,
  зная только адрес почты, запирает человека снаружи; поэтому и сроки
  минутные;
- ответ одинаков для существующего и несуществующего адреса — иначе перебор
  превращается в проверку, кто у нас зарегистрирован;
- счётчики гибнут при перезапуске сервера, и это нормально: перебор после
  перезапуска начнётся заново и упрётся в тот же счётчик;
- считается и вход администратора (`_superusers`): он идёт по своему адресу,
  и пока обработчик висел на одной `users`, самый дорогой пароль в системе
  перебирался без ограничений. Счётчики коллекций держатся врозь — иначе
  постороннему хватало бы стучаться в открытую всем дверь `users`, чтобы
  закрыть вход в админку.

**Человек заперся сам** (забыл пароль и перебрал свой же): ждать минуту.
Снять блокировку принудительно можно только перезапуском бэкенда —
`systemctl restart trainer-pb`, — и это осознанно дорогая операция, чтобы
её не делали по каждой просьбе.

## Проверка обработчиков

Обработчики из `server/pb_hooks` правятся только вместе с прогоном на местном
PocketBase. Причина — в том, как они устроены: **обработчик исполняется в
отдельной машине, и окружающий файл ему недоступен**. Уезжает на сервер
исходник самой функции, а всё, что объявлено рядом с ней, для неё не
существует:

```js
function payloadOf(rec) { /* ... */ }                 // ← за границей обработчика
function check(e) { const p = payloadOf(e.record) }   // ← ReferenceError
onRecordCreateRequest(check, 'records')
```

Падает это не при загрузке, а на каждом запросе, и сервер отвечает отказом на
любую запись, от кого угодно. Именно так обмен однажды встал у всех сразу и в
обе стороны: приложение офлайн-первое, всё написанное ложится в местную базу и
выглядит отправленным, поэтому снаружи поломка неотличима от тишины. Час
переписки и назначений не уехал никуда. Всё, чем пользуется обработчик,
объявляйте **внутри** него.

Стенд поднимается за пять минут:

```bash
# 1. Скачать PocketBase той же версии, что на сервере (pocketbase --version),
#    распаковать во временный каталог, положить рядом наши обработчики:
cp server/pb_hooks/*.pb.js <каталог с pocketbase>/pb_hooks/

# 2. Поднять и завести суперпользователя:
./pocketbase serve --http=127.0.0.1:8090
./pocketbase superuser upsert stand@local.test <пароль>

# 3. Накатить схему и прогнать обмен:
PB_URL=http://127.0.0.1:8090 PB_ADMIN_EMAIL=stand@local.test \
  PB_ADMIN_PASSWORD=<пароль> node server/schema.mjs
PB_ADMIN_PASSWORD=<пароль> node server/hooks-check.mjs
```

`hooks-check.mjs` разыгрывает обмен тренера и клиента теми же запросами, что
шлёт приложение, отдельно пробует подмены — чужой профиль под своим `owner`,
ключ мимо содержимого, сообщение от чужого имени, — перебирает пароль по
одному ящику и проверяет, что у всех записей стоит `seq`. Выходит с ненулевым
кодом, если что-то не сошлось; ту самую поломку он ловит на первой же строке.

Прогон делает вход настоящими запросами, поэтому гонять его **со включёнными
лимитами не нужно**: встроенный ограничитель отрежет его собственные попытки
и проверка упрётся в 429 раньше, чем дойдёт до сути. На стенде лимиты по
умолчанию выключены — так и оставляйте.

Лог обработчика — там же, где и всё остальное: `journalctl -u trainer-pb`.
Ошибка выглядит как `ERROR POST /api/collections/records/records` и следующей
строкой `ReferenceError`.

## Права доступа

Тренер видит и правит данные своих клиентов, больше ничьи. На сервере это
одно правило: `owner = @request.auth.id || owner.trainer = @request.auth.id`.
Связь — поле `trainer` в аккаунте клиента, оно же источник правды для списка
клиентов у тренера.

Коды приглашений закрыты полностью: клиент их не ищет, а отдаёт серверу
через `POST /api/redeem`. Открытый список означал бы, что любой вошедший
может выгрузить чужие коды и привязаться к незнакомому тренеру.

## Если что-то пошло не так

**У пользователя старая версия.** Приложение — PWA, его держит service
worker. Попросите закрыть вкладку и открыть заново или обновить с очисткой
кеша. На телефоне надёжнее закрыть вкладку.

**Данные не доезжают до второй стороны.** Смотрите в админке коллекцию
`records`: есть ли там нужная строка и правильный ли у неё `owner`. Если
строки нет — она не прошла отправку; если владелец не тот — ошибка в
`ownerOf`.

Строки есть, но не доходят — проверьте `seq` фильтром `seq = null`. Забирают
изменения условием `seq > отметки`, и запись без метки не видна никому
никогда: ставит её хук `seq.pb.js` при записи, а трогать её больше некому.
Так уже было — соседний обработчик не дал загрузиться скриптам, и вместе с
ним молчал `seq.pb.js`; час переписки осел на сервере невидимым. Метку
осевшим строкам проставляет `backfill.pb.js` при запуске сервера, так что
достаточно `systemctl restart trainer-pb`. **Правя что-либо в `pb_hooks`,
помните: непрочитанный движком файл унёс с собой все соседние.**

**Тренер пишет, а клиент не получает.** Кабинет строится по локальной
таблице `links`, а право писать за клиента даёт поле `trainer` в его
аккаунте на сервере. Списки расходятся — клиент в кабинете есть, а сервер
его клиентом не считает. Выгрузка такие строки не выбрасывает: она
придерживает курсор (`held` в `push`) и показывает полосу «данные не
уходят», так что написанное уедет само, когда связь починят. Чинится связь
повторным приглашением — поле `trainer` меняет только `POST /api/redeem`.

**Не приходят живые обновления.** Проверьте, что nginx не буферизует поток:
в конфиге должны быть `proxy_buffering off` и длинный `proxy_read_timeout`.

**Письма не приходят.** SMTP не настроен вовсе. Пока это так, ссылка
«забыли пароль» скрыта флагом `VITE_MAIL_ENABLED`. Когда ящик подключат,
включите флаг в сборке.

## Чего пока нет

Список открытых задач, чтобы не браться за них вслепую:

- запросы к базе продуктов Open Food Facts уходят из браузера напрямую за
  рубеж — нужен прокси через свой сервер с кешем;
- отправка сканирует таблицы целиком: по `updated_at` нет индекса, на
  больших объёмах будет тормозить телефон;
- SMTP не подключён;
- требования по персональным данным (152-ФЗ) не реализованы: нет согласий
  с версионированием, журнала доступа, экспорта данных и разделения
  идентифицирующих и медицинских сведений. Сервер не в аттестованном
  контуре, поэтому **на живых данных клиентов работать нельзя** — только на
  тестовых.
